# Merge-policy pilot: shadow phase plan

**Status:** PROPOSED. Merging this document is the freeze: the PR sequence below starts only after it lands, and any change of scope is a change to this file first.

**Basis.** On 2026-09-17 the owner approved continuing the pilot toward a real trust boundary under three constraints: the smallest boundary that is real; shadow first, with enforcement a separate later decision on its own evidence; and explicit kill criteria stated up front. Every PR to this repository is manual click-merge, so the owner's clicks are budgeted like any other resource.

**Evidence basis.** The v2 execution probe (techrecon `docs/audits/merge-policy-review-execution-v2-2026-09-17/OUTCOME.md`, run 35180767886) established that the data-only producer completes a structured review on a GitHub-hosted runner from a protected immutable tag with exact digests, and nothing more: not current-PR review, not identity or execution authentication, not intake or publication, not merge enforcement. All `file:line` references below are to this repository at `0a20fd7` (main on 2026-09-17) and were checked against the code, not the docs.

## 2. Trust boundary for this phase

**Principle:** the smallest boundary that is already proven end to end is _protected tag + approved revision + GitHub-authenticated run and artifact facts + exact digests_, evaluated by a human-held credential. No App in the loop, no OIDC, no new secrets.

| Element                                                    | Trusted for                                                                                                        | Mechanism (existing)                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The owner (GitHub user 11801312, the ruleset bypass actor) | Dispatching producer runs; running the controller; editing control documents by PR                                 | The `gh` identity the CLI uses (`merge-policy-github.mjs:121-152`); `record` binds human events to `gh api user` (`:699`). Needs Actions:read and Contents:read on the producer repo, Contents:read/write on the control repo, PR read on the target.                                                                                |
| A producer run                                             | "This receipt was produced by the approved workflow at the approved commit, attempt 1, and completed successfully" | Lightweight tag under creation, immutability and branch-reservation rulesets; artifact-client checks (`merge-policy-github-artifact.mjs:163-199`, `:216-228`); attempt 1 only, everywhere (`merge-policy-review-producer.mjs:94`; `merge-policy-github-artifact.mjs:438-441`).                                                       |
| Receipt bytes                                              | "These exact bytes came from that run"                                                                             | GitHub archive digest + length (`merge-policy-github-artifact.mjs:592-600`), in-memory extraction (`merge-policy-artifact-zip.mjs:89`), inner SHA-256 and canonical-form checks (`merge-policy-intake.mjs:399-412`).                                                                                                                 |
| Target binding                                             | "The review covered PR N at head H against live base B under authority digest D"                                   | The dispatcher's own durable dispatch record supplies `metadata.target`; the receipt's target must equal it and the live snapshot (`merge-policy-intake.mjs:266`, `:434-437`); the workflow at the approved revision passes inputs to the producer unchanged; model text can never set identity fields (`DATA-ONLY-PRODUCER.md:13`). |
| Control state                                              | Policy, producers, ledger, lock                                                                                    | Control `main`, conditional writes on blob SHA (`merge-policy-github.mjs:201-215`, `:367-372`), framed authority digest (`:87-99`), deletion detection (`:240-248`, `:297-317`).                                                                                                                                                     |

**Untrusted:** PR authors, PR content, PR comments, model output (carried as bounded text), any provenance field inside an artifact, and env-observed runtime claims (re-authenticated through the API).

**Explicitly not covered in this phase:** check publication and required checks (the App stays idle; every result carries `enforcementPublished: false`); dispositions (intake accepts none, `TRUSTED-INTAKE.md:70`); hosted-runner and pinned-action supply chain beyond SHA pins; a compromised owner token; who can dispatch (anyone with Actions:write on the private producer repo, which is the owner); the 2 s reader deadline and the terminal `failed` hold (accepted as operational limits and counted as interventions); the exposure boundary of a repo-wide `MERGE_POLICY_REVIEW_API_KEY` (mitigated by the private, owner-only staging repo; see owner decision 4 before techrecon).

## 3. Shadow mode

**Stage A: the staging repo (`topcoder1/techrecon-merge-policy-staging`).** Prove the mechanics on 5 to 8 owner-authored PRs, including one deliberately failing cycle. **Stage B: techrecon**, gated on Stage A. The human-outcome comparison on real PRs. Stage B needs its own producer tag in techrecon, because the producer must run in the repository whose objects it measures (`merge-policy-github-artifact.mjs:165-171` binds the run to the producer repository ID).

**One shadow cycle, one command, run under the owner's `gh` identity** (by the owner, or by a Claude session on the owner's machine on the owner's say-so per batch; the credential, and so the boundary, is the same):

1. Preflight: `snapshot` for live head, base, `policyDigest` and producers (`merge-policy-github.mjs:216-334`); refuse without paid work if the live base is not an ancestor of the head (record `STALE_BASE`), if the PR is draft or closed, or if a lock or intake hold is unresolved.
2. Dispatch the producer workflow on the protected tag with inputs `{pull_request, head_sha, base_sha, policy_digest}`; write the durable dispatch record before the request (the v2 procedure); capture the run ID.
3. Wait for attempt-1 success; locate the receipt artifact by exact name.
4. `recordReviewIntake` through the adapter (target from the dispatch record; archive fetched once with a 10 s deadline; the second metadata read is one fresh `GET runs/{id}` to re-verify attempt and conclusion).
5. `evaluate` without `--publish` (`merge-policy-github.mjs:631-636`; read-only, test `selftest/test_merge_policy_github.mjs:419`); exit code 1 on hold is normal (`:1039-1040`).
6. Append one JSON record to the shadow log.

**Logged per cycle:** repo, PR, head, live base, authority digest, producers blob SHA, dispatch time, run ID and attempt, artifact ID and archive SHA-256, receipt SHA-256 and `receiptId`, intake outcome (`changed`, ledger revision, or failure code and hold phase), verdict (`decision`, reason codes, open findings with priority, path and title), provider tokens and computed cost, durations, interventions (count + note). Added at triage: the owner outcome (`merged_as_is`, `merged_after_changes`, `closed`), a label per blocking finding (`true_positive`, `false_positive`, `should_be_p3`), and `finding_absent_on_rereview`.

**Human comparison:** a weekly 30-minute triage. A session may pre-fill the outcome (readable from GitHub) and propose a label with its reason for each P0-P2 finding; the owner confirms or overrides. Then `summarize` on the log produces the Section 4 metrics. Because findings persist until disposed (`merge-policy-core.mjs:433-458`; `README.md:45`) and no dispositions are recorded in shadow, a hold caused only by a finding the re-review no longer reports is categorized `needs_disposition`, not disagreement.

**Sample and duration:** Stage A: 5 to 8 PRs over 1 to 2 weeks. Stage B: at least 20 techrecon PRs and 30 reviews, or 4 weeks, whichever comes later, capped by Section 4. Fewer than 20 PRs cannot separate a 50% from a 75% precision rate; more does not change the decision.

**Where the evidence lives:** ledger and lock in the control repo (the existing design); the shadow JSONL and triage in techrecon `docs/audits/merge-policy-shadow-<start-date>/`, matching the v2 OUTCOME convention.

## 4. Kill and success criteria

Cost basis: the pinned model `claude-sonnet-4-6` (`merge-policy-anthropic-review.mjs:7`); the v2 comparison used about 36.9K input and 1.5 to 2.2K output tokens, about $0.14 per review at list prices; the 512 KiB packet cap (`merge-policy-review-comparison.mjs:18`) bounds one review near $0.65.

**Kill (any one stops the phase and parks the pilot; evaluated at each weekly triage):**

- **K1 Agreement.** After 20 blocking findings or 20 Stage B PRs: blocking-finding precision (TP / (TP + FP)) below 50%, or more than 40% of `merged_as_is` PRs held on findings the owner labels false.
- **K2 Cost and fit.** Mean provider cost above $0.75 per review, any single review above $1.50, median reviews per merged PR above 3 (re-reviews forced by base moves), or more than 50% of Stage B PRs refused by the collector (`STALE_BASE`, or the file and byte limits at `merge-policy-review-comparison.mjs:9-21`).
- **K3 Operations.** More than 2 operator interventions in any week (manual control-repo edits to clear `failed` holds or retained locks, redispatches), or intake failure on 2 of any 5 consecutive successful producer runs.
- **K4 Security (immediate, no threshold).** Any credential or token in logs, artifacts, errors or the shadow log; any receipt admitted from a non-tag ref, attempt > 1, or with a target not equal to the dispatch record; any workflow change reaching the tag without the packet procedure.
- **K5 Budget.** More than 5 owner click-merges attributable to this phase (2 for Stage A, 1 for Stage B, 2 in reserve), or calendar date 2026-10-31 without the Stage B sample.

**Success (all required to open the enforcement decision):** the Stage B sample reached; precision at least 70%; intake success on at least 90% of successful producer runs; at most 1 intervention per week over the last 3 weeks; mean cost at most $0.50 per review; zero K4 events; at least 3 `pass` verdicts on merged PRs and 3 holds with owner-confirmed true positives; a written answer to owner decision 6 (who may dispose findings).

## 6. Owner decisions

Each with a recommendation; the default applies if this document merges without a change.

1. **Include Stage B (techrecon) in this phase?** Recommend yes, gated on Stage A passing 5 cycles with no intervention. Without it the agreement evidence is weak. Default: yes.
2. **Reviewability of PRs behind `main`.** Recommend: preflight refuses (`STALE_BASE`, no paid work) and the rate feeds K2; do not change the engine's live-base binding now. Default: refuse.
3. **Tag protections.** Per-tag rulesets (three per tag, as v1 and v2) or one pattern-based set for `merge-policy-review-*`. Recommend pattern-based, created once, so each reviewer revision costs one tag push. Default: pattern-based.
4. **Secret placement.** Staging: keep the repo secret (private, owner-only). Techrecon: an environment restricted to the tag pattern holding a dedicated low-limit key, never `ANTHROPIC_API_KEY`. Default: as recommended; Stage B is blocked otherwise.
5. **Lane actor ID (`publisherActorId`).** Must differ from every PR author (`merge-policy-intake.mjs:366-369`). Recommend the staging App's bot user ID (the future publisher), even though the App is idle. Default: the App bot ID; fallback a synthetic ID as in `README.md:36-45`.
6. **Who disposes findings.** With the owner as PR author, the owner cannot dispose (`merge-policy-core.mjs:352-353`); on a one-person repository no independent disposer exists. Recommend: no dispositions in shadow; decide before enforcement whether a second principal or a re-review-based closure is acceptable. Default: defer, as a success-criteria gate.
7. **Reconciling `failed` holds and retained locks.** Recommend manual control-repo commits for this phase, counted as interventions (K3); add a `reconcile-intake` command only if K3 trends toward the limit. Default: manual.
8. **Where the shadow log lives.** Recommend techrecon `docs/audits/merge-policy-shadow-<date>/`. Default: as recommended.
9. **Budget numbers** (N = 20 PRs, D = 2026-10-31, M = 5 merges, the cost thresholds). Defaults as in Section 4.

## 7. Open risks

- The live-base binding plus ancestor-only measurement may make most techrecon PRs unreviewable or force repeated reviews; K2 measures this, and the fix (merge-base binding) would be an engine change outside this phase.
- A 2 s reader deadline against real GitHub latency may produce chronic `failed` holds; the adapter's prefetch design mitigates it, and K3 catches the residue.
- Findings never close without a disposition, so shadow verdicts will show more holds than a human would; the `needs_disposition` category keeps the comparison honest, but the enforcement design depends on decision 6.
- The dispatch inputs are trusted because only the owner can dispatch a private repository's workflow; any broadening of Actions:write on the producer repo silently widens the boundary.
- Live configuration this repository cannot verify (App permissions, control-repo protections, the existence of control documents) must be re-read before Stage A, as `TRANSPORT-PROBE.md:40-48` already requires.
- The reviewer prompt and structured schema are unchanged from v2; one in three earlier live outputs exceeded the old caps; the new caps hold locally, but K3 will surface any new shape of provider failure.
